# PRODUCT M6 — Build Mode

Status: implementation and deterministic verification complete on the PRODUCT M6 branch; final governance-head PR CI and merge evidence pending.

PRODUCT M6 turns Odin's existing Project, Workspace, Memory, Run, Skill, Tool and Verification authorities into an end-to-end product-building workflow. It does **not** introduce a second executor, mission state machine, task graph, Skill runtime, Workspace, Memory store, verification engine or Artifact authority.

## Product flow

```text
Build request
→ Product Spec / Build Blueprint / Design System in PRODUCT M2 Workspace
→ meaningful project decisions promoted through PRODUCT M3 Memory when explicitly requested or seeded from authoritative Build documents
→ canonical Hosted Run / Mission Runtime
→ PRODUCT M5 Skill selection through the existing M10 → M23 path
→ existing scoped repository/workspace tools under M25/M3 authority
→ existing quality + verification authority
→ content-bound isolated Preview
→ bounded delta iteration
```

## Product Spec

Build start creates a real editable Project-scoped Workspace document with goal, target user, problem, user workflows, screens, functional requirements, constraints, non-goals and success criteria. It is persisted through `WorkspaceOsStore`; Build Mode keeps only canonical Workspace item references in Build events. The initial Product Spec is promoted through the canonical Memory Brain with Workspace provenance rather than copied into a parallel store.

## Blueprint

The Blueprint is a real editable Workspace document. Its structure covers screens/flows, components, data model/backend needs, Connections, security requirements, implementation stages and verification plan. It remains project data and never acquires system-policy authority merely because it was generated by Build Mode.

## Design System

The Design System is another Project Workspace document and sets project-specific direction for tokens, typography/spacing, components, responsive layout, loading/empty/error states and interaction states. The implementation prompt explicitly rejects generic AI-SaaS replacement of existing product architecture.

## Real implementation and canonical Runs

Build execution is a canonical Chat/Hosted Run. Greenfield builds use the existing internal `NeonWorkspace`; existing-application builds use the already-connected GitHub Workspace path. Both execute through the existing repository tool contract (`repo_read/search`, `repo_patch`, `repo_quality`) and canonical Run lifecycle. A Build request is bound to a Run only after the server verifies that the Run belongs to the same Project.

M6 does not accept answer-only code as implementation evidence. The deterministic acceptance fixtures require actual file writes and a passing quality command before the Run can complete.

## Skills

Build Runs do not invent a Build-specific Skill runtime. They continue through the PRODUCT M5 Hosted Run integration, where installed Product Skills are discovered and selected through M23 and exact M10 package identity. Run Center projects only canonical `skill.selected`, `skill.loaded` and `skill.result` events; Build UI does not dispatch those events itself.

## Memory

The initial Product Spec is promoted from its actual Workspace source through the existing Memory Brain. Optional delta decisions use explicit Project-memory writes only when requested. Transient compiler output, test logs and implementation noise are not automatically persisted as durable product truth. Workspace-origin provenance lets later source changes become visible as stale Memory rather than silently remaining current.

## Preview

Preview is isolated and explicitly separate from Published/Deployed/Production state. Its revision is the SHA-256 identity of the current previewable output file set, excluding editable planning documents. The hosted preview requires the caller's expected revision to match the current revision and retains the existing restrictive CSP/opaque iframe model with external connections blocked.

Desktop, tablet/iPad and mobile widths are product controls over the same revision, not separate fake renders.

## Visual → source mapping

The first visual-editing foundation uses explicit `data-odin-source` references. A mapping is exposed only after path normalization and stable source-id validation; traversal and uncertain/unsafe mappings are hidden or rejected. Delta prompts may bind to a verified mapping, but a mapping never expands repository, tool or policy authority. If no verified mapping exists, Odin is instructed to inspect files and make the smallest safe delta instead of guessing a source target.

## Delta iteration

Iterations preserve the existing Project and Build state. They create a new canonical request/Run with the prior Workspace/repository as the starting point, apply only the requested delta, rerun the existing quality gate and produce a new Preview revision from the resulting files. They do not regenerate the application from scratch.

## Deterministic acceptance

### Acceptance #1 — Student exam planner

The test requests `Build a simple student exam planner.` through `ChatEngine` and the canonical coding tool path. The fixture produces real `index.html`, `styles.css` and `app.js`, including dashboard/exam list/create-exam fields for subject/date, responsive behavior, empty state and explicit browser persistence. It runs the quality tool, reaches canonical COMPLETED only after passing evidence and assembles a real isolated Preview revision.

A consecutive delta request changes only the Add-exam button sizing, preserves `index.html`, reruns quality and verifies the new result rather than rebuilding the application.

### Acceptance #2 — existing application dark mode

The test starts from an existing application fixture, requests `Add dark mode.`, reads the current source, patches only the scoped stylesheet, runs the existing quality gate, preserves the unchanged HTML architecture and verifies a real `file.changed` event before completion.

## Security boundaries

Build content — including repository text, Workspace documents, Skills and generated specs — is untrusted data. It cannot expand M25/M3 tool authority, network access, credentials, database/deployment permissions or approval policy. Existing repository path normalization, symlink confinement, secret screening, RLS/actor scope, Project/Run binding, Skill integrity, tool grants, verification evidence, budgets and retry ceilings remain authoritative.

M6-specific regressions add content-bound Preview identity, Project/Run binding, canonical Build-event integrity, safe visual mapping, traversal rejection, delta preservation and no deployment claim. The wider repository suite continues to cover prompt-injection/Skill intake, secret exfiltration, cross-scope access, path/symlink escapes, arbitrary shell/network denial, forged evidence, sandbox/network policy, high-impact approvals and bounded repair/retry behavior.

## Resume and budgets

Build execution inherits durable Run/checkpoint behavior from PRODUCT M4 and the existing ChatEngine. Reload/browser close does not create a second mission. Interrupted work follows canonical recovery semantics and uncertain calls are not replayed blindly. Token/tool/call ceilings and failure circuit breakers remain the canonical bounds; Build Mode does not implement an unbounded repair loop.

## Known boundaries

- Greenfield PRODUCT M6 intentionally supports the maintained static-web target; it does not pretend arbitrary framework scaffolding is already available.
- Existing-app builds require an actual selected GitHub repository when repository mode is used.
- Preview proves the repository/workspace revision and isolated render contract, not production deployment or all real-browser persistence semantics.
- Visual editing acts only on explicit verified source mappings; uncertain mappings fail honestly.
- PRODUCT M6 performs no autonomous paid purchase or destructive production deployment/database action.
